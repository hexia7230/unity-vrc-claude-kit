# ナレッジと作業ログの残し方

## 3 種類のファイル
- `docs/knowledge/vrc-sdk-ndmf-ma-facts.md` 型の「事実集」 — SDK・NDMF・MA・lilToon から読み取った事実と落とし穴。確認済みのものだけ。追記のたびに日付の見出しを付ける。
- `docs/knowledge/<製品>-unverified.md` — 製品ごとに 2 節: 「確認済み (エディタ)」(方式、数値、テスト結果、プレビュー画像の場所)、「未確認 (実機)」(番号付き)。実機報告が来たら該当項目を直し、「報告 (日付): ...」を足す。
- `docs/worklog/<日付>.md` — 節目ごとに追記 (その日にやったこと、原因、対処、コミットの要点)。

## 書き方のルール
- 推測は「未確認」と明記する。事実を書くときは、どう確認したか (コンパイルで確認、バッチで確認、実機で確認 + 日付) を一言添える。
- 数字は具体的に (0.08、4.5 秒、3 mm)。同じことをもう一度試せるように、コマンドやファイル名も残す。
- 原因が分からなかったこと、試して効かなかったことも書く (同じ道を戻らないため)。
- 製品の README/Booth 文と混ぜない。配布物は絵文字なしの日本語。ナレッジは内部向け。

## 報告の型 (ユーザーへ)
1. 先に結果 (できた / できていない / 確認できていない)。
2. 何をしたか (仕組みを 3 行ほどで)。
3. 確認したこと (テスト、写真のパス)。
4. 実機で見てほしいこと (最も大きい未確認を最初に、代替案も)。
5. 次の判断が要ることだけ質問する。

## コミット
- 製品ごと・修正ごとに分ける。メッセージは日本語で「何をしたか + 要点の箇条書き」。worklog と knowledge の更新は同じコミットに入れてよい。
- ユーザーの Git の身元 (`-c user.name=... -c user.email=...`) を使い、共同作成者の行を付ける。
- 外部に出る操作 (push、公開、送信) は、頼まれた範囲だけ行う。
